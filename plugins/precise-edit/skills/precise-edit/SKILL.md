# Precise Edit

Change existing content with the smallest exact-match edit that does the job. Never regenerate a whole file, document, artifact or canvas to change part of it: full rewrites silently drop unrelated content, revert earlier fixes, break formatting and line endings, and turn a three-line change into an unreviewable diff.

## Pick the precise tool

| Environment | Use | Never use on existing content |
|---|---|---|
| Claude Code | `Edit` (`old_string` → `new_string`; `replace_all` only when every occurrence must change) | `Write` over the file; `sed -i`, `perl -pi`; `> file`, `cat <<EOF > file`, `tee`; `Set-Content` / `Out-File`; scripts that read-modify-write |
| Claude.ai chat, Claude Cowork | `str_replace` on files; the artifact `update` command | `create_file` over an existing path; artifact `rewrite` for a local change; bash rewrites |
| Codex | `apply_patch` with `*** Update File:` hunks | `*** Add File:` on an existing path; Delete + Add of the same file; `sed -i`; `cat > file <<EOF`; Python/Node write-back scripts |
| ChatGPT canvas | `update_textdoc` with a pattern that matches only the passage being changed | a `.*` pattern that replaces the whole canvas |
| ChatGPT Work, other agents | the tool's replace / patch / edit operation | any "write the whole file" operation on an existing file |
| Plain chat (no file tools) | for long text, show only the changed passages with enough surrounding text to locate them, then offer the full version | silently re-printing the entire document with untracked changes |

## Workflow

1. **Read first.** View the current content of the region being changed - fresh, not from memory. Files change after formatters, earlier edits, or the user's own edits.
2. **Choose the anchor.** Select the smallest snippet that is unique in the file: usually the target lines plus 1-3 lines of context. Copy it exactly - indentation, tabs vs spaces, trailing whitespace, quote style, line endings.
3. **Strip viewer decorations.** Never include line-number prefixes, `cat -n` gutters or diff markers from viewer output in the anchor.
4. **One logical change per edit.** Several sites mean several edits. Do not merge distant sites into one giant anchor.
5. **Verify.** Re-read the edited region, or run the tests, linter or a diff. Confirm nothing outside the intended change moved.

## When an edit fails

- **No match**: re-read the exact lines. Check tabs vs spaces, trailing spaces, CRLF vs LF (common on Windows), smart quotes, non-breaking spaces, wrapped lines, and whether an earlier edit already changed the text. Retry with a shorter anchor taken from the fresh view.
- **Multiple matches**: extend the anchor with neighbouring lines until it is unique. Use replace-all only when every occurrence must change.
- **Patch does not apply (Codex)**: re-read the file, regenerate the hunk with exact context lines, keep hunks small.
- **Still failing after two attempts**: narrow down - view a smaller range, anchor on a single distinctive line, and build the change from several small edits.
- **Never** fall back to rewriting the file, `sed -i`, redirection or a script as a workaround. If the edit truly cannot be made, stop and explain the problem.

## When a full rewrite is acceptable

- The file is new or empty.
- The file is generated (lockfile, build output, snapshot) and is regenerated by its own tool, not by hand.
- The user explicitly asks for a complete rewrite or regeneration.
- Nearly every line changes **and** the file is short - say so explicitly before doing it.

If a guard hook blocks a call with `precise-edit: blocked ...`, follow its message and switch to an exact-match edit. Do not edit the guard's configuration, rename files or reach for another tool to get around it. If the user wants a full rewrite, tell them how to allow it.

## Edit hygiene

- Preserve the file's existing style: indentation, quote style, line endings, trailing newline, import order.
- Do not reformat, re-wrap or tidy lines that are not part of the change.
- Keep comments and unrelated code exactly as they were.
- For large refactors, prefer many small, verifiable edits over one sweeping change.
